多数用户直接用[桌面应用](https://openworklabs.com/download)就够了。自托管适合希望 OpenWork 跑在自己的服务器、VPC 或私有云里，然后让桌面应用远程连上去的团队。

想要托管工作区、团队 Collections 或共享提供商，又不想自己运维基础设施？请改用 [OpenWork Cloud](/cloud/get-started)。要在全公司范围推开？就 [Enterprise](/cloud/enterprise) 可以[约个会议](https://calendar.app.google/86QpCENvhfEzDFLu5)。

<Note>
  在规划生产环境基础设施之前，想先试一下自托管的控制平面？启动[只拉取镜像的 Docker Compose 评估方案](/self-host/evaluate-with-docker-compose)即可。它使用已发布的镜像，不需要 clone 或构建仓库。
</Note>

## 部署方式

| 方式 | 适合 | 指南 |
| --- | --- | --- |
| Docker Compose | 在单台机器上做评估 | [用 Docker Compose 评估](/self-host/evaluate-with-docker-compose) |
| Helm 部署在 Amazon EKS | 在 AWS 上的生产环境，配 Amazon RDS for MySQL | [部署到 AWS](/self-host/deploy-to-your-cloud/aws) |
| Helm 部署在 Azure AKS | 在 Azure 上的生产环境，配 Azure Database for MySQL | [部署到 Azure](/self-host/deploy-to-your-cloud/azure) |
| Helm 部署在 Google GKE | 在 Google Cloud 上的生产环境，配 Cloud SQL for MySQL | [部署到 Google Cloud](/self-host/deploy-to-your-cloud/google-cloud) |
| 其他容器平台（例如 Amazon ECS/Fargate） | 不运行 Kubernetes 的团队 | 使用已发布的镜像，并参照下文的各服务边界 |

经过验证的生产路径是把已发布的 Helm chart 部署在托管 Kubernetes 上。仓库里没有提供 Terraform 模块或 ECS 任务定义。如果你要在 ECS/Fargate 或其他容器平台上运行，请用自己的基础设施代码，从 GHCR 部署已发布的 `openwork-den-web`、`openwork-den-api` 和可选的 `openwork-inference` 镜像，并对齐 chart 做的事：Den web 监听 `3005` 端口，Den API 监听 `8788` 端口，在 Den API 接流量之前先执行数据库迁移，使用 MySQL 8 兼容的数据库，并在两个主机名前面都放 HTTPS。通用架构见 [部署到你自己的云](/self-host/deploy-to-your-cloud/overview)，镜像细节见 [Docker 打包](https://github.com/different-ai/openwork/tree/dev/packaging/docker)。

## 你要部署什么

OpenWork 拆分成几个常规服务：

- **OpenWork 应用**：大家实际使用的桌面或 web 客户端。
- **OpenWork 服务器**：工作区运行时和 API。桌面应用运行它自己的本地服务器；自托管服务器则为其 web 客户端提供运行时。
- **Den web**：如果你想要云端式的部署，用它来做登录和组织管理。
- **Den 控制器**：负责认证、团队、访问和开通的控制平面。
- **OpenWork Gateway**：来自 `ee/apps/gateway` 的可选模型请求路由与计量服务，也包含既有的 OpenWork Models 代理。它不是另一个独立的 `den-gateway` Web 代理。

只要一个独立的工作区运行时，部署 OpenWork 服务器并使用它的 web 客户端即可。桌面应用不提供共享工作区或连接远程工作区，其内嵌服务器只监听回环地址。如果你同时还需要 OpenWork Cloud 式的账户、团队和组织管理，就再部署 Den web、Den 控制器，以及可选的 OpenWork Gateway。

Kubernetes 安装请使用已发布的 Helm chart：

```bash
helm upgrade --install openwork-ee oci://ghcr.io/different-ai/charts/openwork-ee \
  --version <chart-version> \
  -f values.prod.yaml
```

`--version` 用于锁定 chart 版本。请检查它的 `image.tag`、`appVersion` 和各组件镜像覆盖项，把你要用的镜像钉死；较早发布的 chart 可能默认使用浮动标签 `latest`。除非在内部做了镜像，否则这些镜像是 GHCR 上的 `openwork-den-api`、`openwork-den-web` 和可选的 `openwork-inference`（沿用的 Gateway 仓库名）。仅仅升级 chart，并不会让旧镜像获得 Gateway 支持。

Gateway 的部署配置，请使用 `0.2.0` 及之后引入的 chart 实现，并搭配 capability-version-1 发布中相匹配的 Den API、Den Web 和 Gateway 镜像。checkout 里那个占位的 `appVersion` 不是可用的镜像建议。请先按 [启用 OpenWork Gateway](/self-host/gateway) 做显式配置，并在任何已有安装推这些镜像之前，按 [安全升级 Gateway](/self-host/gateway-upgrade) 完成静默状态下的数据库切换。配置到位之后，Gateway 对所有组织的管理员都是 GA 的，不需要组织级开关，也不需要平台管理员授权。`GATEWAY_ENABLED` 和 `deploymentCapabilities.aiGateway` 仍然是安装侧的配置检查项：只写遗留的 `inference.enabled: true` 并不能启用 Gateway 管理，OpenWork Models 的计费也是独立计算的。

已验证的提供商路径请在 [部署到你自己的云](/self-host/deploy-to-your-cloud/overview) 里选择。公开指南覆盖 AWS、Azure 和 Google Cloud，包括托管 MySQL、入口、DNS、TLS、迁移，以及安全地创建第一个管理员。

## 我们如何部署托管的工作进程

我们的托管部署用 Render 跑长驻服务和工作者供给（worker provisioning）。Render 提供服务部署、环境变量、健康检查、日志和工作进程构建，不需要我们直接运维底层的 AWS 服务。如果你想更贴近 AWS 自己来做，可以在 ECS/Fargate、EC2、Kubernetes 或其他容器平台上复用同样的服务边界。

在生产环境里，托管的 OpenWork 把 Cloud 应用和 Den 控制器作为可横向扩展的 Render 服务运行，至少两个实例。Render 会在健康实例之间做负载分发，把故障实例移出路由，并重启失败的实例。Den 控制器的应用实例是无状态副本；共享的控制平面状态存在 PlanetScale 里。

生产形态并不复杂：

- 每个对外服务前面都放 HTTPS。
- 暴露 OpenWork 服务器/工作进程的 URL，而不是裸的 opencode。
- 工作区和数据路径放在持久化存储上。
- 用环境变量配置 `DEN_BASE_URL`、令牌和提供商凭证。Den 的 Better Auth URL、CORS/受信任源站、API 默认值、MCP 资源默认值和 web 应用主机白名单都从 `DEN_BASE_URL` 推导，除非你为拆分源站的拓扑设置了兼容变量。
- 在 Den 控制器接流量之前先执行 Den 数据库迁移。

容器化的服务，请从仓库里的 [Docker 打包](https://github.com/different-ai/openwork/tree/dev/packaging/docker) 开始。

## 数据库与存储

- 工作进程运行时使用文件系统状态，以及工作区/数据挂载路径内的 opencode SQLite 数据。
- Den 控制平面使用 MySQL 兼容的数据库。本地 Docker 用 MySQL 8.4；生产可以用标准 MySQL，或 PlanetScale 兼容的凭证。
- 托管的 OpenWork 用 PlanetScale 存放 Den 的控制平面状态。PlanetScale 生产集群提供一个主库和至少两个副本，跨三个可用区，并具备托管故障转移与自动备份。
- 当前的 Den 部署路径不需要 Postgres。

生产环境请显式配置加密：

- 为 MySQL 兼容数据库、数据库备份、对象存储、工作进程卷，以及可能含运维元数据的日志开启静态加密。
- 应用到数据库的流量要求 TLS。在 OpenWork 里，`sslmode=require`、`sslmode=verify-ca`、`sslmode=verify-full` 和 `sslaccept=strict` 都会校验服务端证书链和主机名（Den 的 MySQL 客户端把 `verify-ca` 视同 `verify-full`），因此服务端证书必须能链到一个受信任的 CA，并且其 SAN 中包含数据库主机名。请使用 `sslmode=verify-full`，并通过数据库平台或 Helm 的 `customCa` 提供私有 CA bundle。只有 `sslaccept=accept` 是只加密但不校验证书；请把它留给冒烟测试。
- 本地 Docker 的数据库默认值只用于开发；生产凭证请使用预先创建好的 Secret 引用。
- 设置一个至少 32 个字符、且唯一不重复的 `DEN_DB_ENCRYPTION_KEY`。OpenWork 用它加密数据库中选定的敏感列，但它不能替代基础设施层面的静态加密。

自托管的生产部署，请使用带自动故障转移和备份的托管 MySQL 兼容数据库，或者自己提供同等水平的冗余。请把恢复流程、备份保留期、恢复时间目标、恢复点目标，以及负责故障转移和恢复的人员或团队写进文档。

## 认证与 SSO

Den 使用 Better Auth。它跑在你的部署里，用你的数据库，靠你的 `BETTER_AUTH_SECRET`、`DEN_BASE_URL` 和可选的 GitHub/Google OAuth 凭证来配置。`BETTER_AUTH_URL`、受信任源站、CORS 源站和 web 应用主机名都从 `DEN_BASE_URL` 推导；只有在你有意做迁移，或运行拆分源站拓扑时才设置那些旧变量。

私有部署应当保持公开注册关闭，并使用一次性的[首个管理员设置流程](/self-host/deploy-to-your-cloud/first-administrator)。配置所有者或平台管理员邮箱既不会创建账户，也不会创建密码，OpenWork 也不提供默认管理员密码。

SSO（SAML/OIDC）正在当前推广中，其设计就是对接你自己的身份提供商。启用之后，回调 URL 和受信任源站都应指向你自托管的 Den web/控制器主机。

对于隔离的 Kubernetes 部署，如果没有批准对 Have I Been Pwned 的 Pwned Passwords 区间 API 的出站访问，Helm chart 默认会关闭外部泄露密码查询。邮箱/密码登录的锁定仍然在本地生效。如果你的部署批准了这项外部查询，请在 Helm 里开启。更完整的隔离清单见 [离线（air-gapped）部署](/start-here/air-gapped-deployment)。

如果你不部署 Den，工作进程的访问是基于令牌的，使用 `OPENWORK_TOKEN` 和 `OPENWORK_HOST_TOKEN`。

## 最小可用技术栈

### OpenWork Cloud 与桌面应用

OpenWork 这种云形态的自托管由三个主要部分组成：

- Next.js 前端
- 配 MySQL 数据库的 Node.js 后端（Hono）
- Electron/React 桌面应用

桌面应用应指向 Den web 的 URL。启动时它从 Den Web 读取 `${DEN_BASE_URL}/api/runtime-config`，并把返回的 `denApiUrl` 作为 Den API 与 MCP 流量的唯一依据。设置了 `DEN_API_PUBLIC_URL` 时 Den Web 就返回它，否则按 `api.${DEN_BASE_URL}` 确定性地推导 API 源站。Den Web 上必须设置 `DEN_BASE_URL`。`DEN_API_BASE` 是 Den Web 内部访问 Den API 的服务端专用 URL，它绝不会返回给桌面应用。

- API 默认值：`https://api.<den-web-host>/v1/...`
- MCP 默认值：`https://api.<den-web-host>/mcp/...`

自托管部署请把桌面的 `baseUrl` 配置为公开的 Den web 源站，并确保成员桌面设备能够访问 `${DEN_BASE_URL}/api/runtime-config`。如果 `api.${DEN_BASE_URL}` 上没有可用的 API，请在 Den Web 上设置 `DEN_API_PUBLIC_URL`，指向你希望桌面使用的那个可外部访问的 API 源站。

这三部分覆盖了大部分功能，但不包括：

- 通过沙箱远程执行代码
- 分析
- 基于 OpenTelemetry 的遥测
- 用于邀请和生命周期消息的事务性邮件

## 可选的第三方服务

OpenWork 的核心运行时并不依赖很多第三方服务。下面这些是可选的，或只与特定部署有关：

- Render：我们目前的托管服务与工作进程部署路径。
- Daytona：云端工作进程的可选沙箱提供商。
- Vercel：可选的 Den web 托管与工作进程 DNS 自动化。
- PostHog：面向公开 web 界面的可选分析。可以用 `NEXT_PUBLIC_POSTHOG_HOST` 指向自托管的 PostHog；不想做分析，就在你的自托管 web 构建里删除或清空那个 key。
- Loops：可选的用户同步与生命周期消息。
- GitHub/Google OAuth：为 Better Auth 提供的可选社交登录提供商。
- GitHub 连接器应用：可选的仓库连接器，用于从 GitHub 导入并同步插件或市场。Helm 安装请见 [GitHub 连接器的设置指南](/zh/start-here/github-connector-helm)。

## 不想自己运维？

跳过服务器。[**OpenWork Cloud**](/cloud/get-started) 为你的团队跑托管的工作进程。

Cloud 还提供一批组织级能力，否则你得自己造：[Collections](/cloud/share-with-your-team/collections)、[共享 LLM 提供商](/cloud/share-with-your-team/managed-llm-provider)、[RBAC](/cloud/members-and-rbac) 和 [OpenWork Web](/cloud/run-in-the-cloud/shared-workspace)。

## 更大规模上线，需要支持？

如果你要在 150\+ 人规模的公司里推开 OpenWork，单台自托管服务器可能会越来越难维护。

到这个规模，我们的客户通常想要：

- **SSO（SAML/OIDC）**，让大家用公司已有的身份体系登录
- 跨会话、工具调用和模型用量的**审计日志**
- 集中而不是按工作区执行的**模型与工具放行名单**
- 结合自己网络与合规约束的 **VPC / 本地部署**
- 来自我们团队的**支持与上线协助**，而且不限于在 GitHub 上提问。

你可以看 [**Enterprise**](/cloud/enterprise) 页面，或者[约一个 30 分钟的会议](https://calendar.app.google/86QpCENvhfEzDFLu5)。
