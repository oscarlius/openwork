---
title: "Okta SAML SSO"
description: "通过 SAML 把 Okta 连接到 OpenWork Cloud 或自托管的 OpenWork 部署"
---

用这份指南让组织成员通过 Okta 应用集成登录 OpenWork。它同时适用于 OpenWork Cloud，以及拥有公网 HTTPS Web origin 的 Helm 部署。

SAML 登录跑通之后，再用 [Okta SCIM 开通](/cloud/scim-okta)同步成员和组。

## 开始之前

你需要：

- OpenWork 组织的所有者。
- 一位能创建并指派应用集成的 Okta 管理员。
- 对你要与该连接绑定的邮箱域名拥有 DNS 控制权。
- 最终确定的 OpenWork Web origin(HTTPS)，例如
  `https://openwork.example.com`。

在你完成域名验证、跑通一次真实认证测试并显式启用 SSO 之前，OpenWork 会把新的 SSO 配置保持为禁用状态。配置期间请保留密码登录作为恢复通道。

<Note>
对于 Web 与 API 分开部署的 Helm 环境，请使用 OpenWork 在 **Settings → SSO** 中显示的 URL，不要把它们的主机换成另一个 API origin。SAML 使用部署所配置的 auth origin；当 `/api/auth` 通过 Web 主机代理时，通常就是公网 Web origin。
</Note>

## 1. 获取组织 ID

在 OpenWork 中选择该组织，打开 **Settings → General**，复制组织 ID。OpenWork 按下面的格式生成 SAML 提供商 ID：

```text
openwork-sso-<organization-id>
```

对应的断言消费服务 URL 是：

```text
https://<openwork-web-origin>/api/auth/sso/saml2/sp/acs/openwork-sso-<organization-id>
```

保存 OpenWork 连接后，你可以再次确认生成的确切 URL。

## 2. 创建 Okta 的 SAML 应用

在 Okta Admin Console 中：

1. 打开 **Applications → Applications**。
2. 选择 **Create App Integration**。
3. 选择 **SAML 2.0**，然后点击 **Next**。
4. 把 **App name** 设为 `OpenWork` 或其他一眼能认出的名称。
5. 点击 **Next**。

## 3. 在 Okta 中配置 SAML

在 **General** 下填入：

| Okta 字段 | 值 |
| --- | --- |
| Single sign-on URL | 第 1 步得到的 OpenWork ACS URL |
| `Use this for Recipient URL and Destination URL` | 启用 |
| Audience URI (SP Entity ID) | OpenWork 的 Web origin，例如 `https://openwork.example.com` |
| Default RelayState | 留空 |
| Name ID format | `EmailAddress` |
| Application username | `Okta username` |

展开 **Show Advanced Settings** 并确认：

- **Response**：`Signed`
- **Assertion Signature**：`Signed`
- **Signature Algorithm**：`RSA-SHA256`
- **Digest Algorithm**：`SHA256`
- **Assertion Encryption**：`Unencrypted`

OpenWork 要求断言必须签名。请让 Okta 用户名和 NameID 等于那个稳定的工作邮箱，SCIM 之后会以 `userName` 发送同一个值。

点击 **Next**，在需要时把该集成标记为内部应用，然后点击 **Finish**。

## 4. 把 Okta 的值填入 OpenWork

在 Okta 应用的 **Sign On** 页签选择
**View SAML setup instructions**，复制：

- **Identity Provider Single Sign-On URL**
- **Identity Provider Issuer**
- **X.509 Certificate**，包含 `BEGIN CERTIFICATE` 和
  `END CERTIFICATE` 两行

在 OpenWork 中打开 **Settings → SSO**，选择 **SAML**，填入：

| OpenWork 字段 | Okta 的值 |
| --- | --- |
| IdP Issuer URL | **Identity Provider Issuer** |
| Domain | 成员的邮箱域名，例如 `example.com` |
| SAML Entry Point | **Identity Provider Single Sign-On URL** |
| Audience URL | 留空，使用已配置的 OpenWork auth origin |
| IdP Certificate | **X.509 Certificate** |

保存连接。OpenWork 随后会显示包括 **Sign-in URL**、**Redirect URL**、**ACS URL** 和 **Metadata URL** 在内的配置值。请把生成的
**ACS URL** 与 Okta 的 **Single sign-on URL** 逐字符比对。如果你希望 Okta 磁贴发起同一个按组织的流程，也把生成的 OpenWork **Sign-in URL** 复制回 Okta。

此时保存下来的配置仍是禁用状态。

## 5. 验证邮箱域名

在 **Domain verification** 下选择 **Request token**，然后为该邮箱域名创建一条 DNS TXT 记录：

| DNS 字段 | 值 |
| --- | --- |
| Type | `TXT` |
| Name | `_better-auth-token-<provider-id>` |
| Value | OpenWork 显示的 token |

例如，`example.com` 对应的提供商 `openwork-sso-org_123` 会得到：

```text
_better-auth-token-openwork-sso-org_123.example.com
```

如果 DNS 控制台会自动补上区域后缀，名称栏里只填 `_better-auth-token-<provider-id>`。Token 有效期为七天。TXT 记录能被公网解析后，在 OpenWork 中选择 **Verify domain**，并确认连接显示 **Domain verified: Yes**。

## 6. 在 Okta 中指派一个测试用户

在 Okta 应用中：

1. 打开 **Assignments**。
2. 选择 **Assign → Assign to People**。
3. 指派一位 OpenWork 所有者，或另一个你可控的测试用户。
4. 确认应用用户名就是该用户稳定的工作邮箱。

在测试用户能跑通完整流程之前，不要指派大范围的组。

## 7. 在 OpenWork 中测试并启用 SSO

Okta 指派和域名验证都完成后：

1. 在 OpenWork 的 **Settings → SSO** 中选择 **Enable Config** 或 **Enable SSO**。
2. 在 **Test SSO before enabling it** 对话框中选择 **SSO Login**。
3. 在弹出的独立窗口中完成 Okta 认证。
4. 返回 OpenWork，确认显示 **Authentication test successful**。
5. 选择 **Enable SSO**。

测试过程中请确认：

1. OpenWork 跳转到了预期的 Okta 租户。
2. Okta 认证了被指派的用户。
3. Okta 把断言发送到生成的 OpenWork ACS URL。
4. OpenWork 把用户带回预期的组织。
5. OpenWork 中的成员身份使用的邮箱，与 Okta 作为 NameID 发送的完全一致。

在测试成功后你没有显式启用之前，组织成员看不到 SSO 入口。如果测试成功后又修改了 SSO 配置，请在启用前重新测试一次。测试链接五分钟后失效。

只有这一步成功之后，再去配置 SCIM。

## 即时开通与密码注册

在为已验证的域名启用 Okta SAML SSO 之后，OpenWork 的标准登录流程会把该邮箱域名的用户导向组织的 SSO 流程。用户成功完成 SAML 登录后，OpenWork 可以即时(just in time)为其创建组织成员关系，默认角色是 `Member`。

JIT 开通只发生在 SAML 认证成功之后。用同一邮箱域名创建邮箱/密码账户，不会把用户加入组织，也不会创建由 SCIM 管理的身份。如果该用户之后完成了 SSO，OpenWork 可以把匹配的账户关联起来，并通过 SSO 开通组织成员关系。

OpenWork 不会把 `role`、`groups`、`admin` 这类 SAML 属性转换成更高的组织角色。角色由所有者在 OpenWork 中指派；所有者的变更要走所有权转移。要基于组授予 Admin，请先配置 [Okta SCIM 开通](/cloud/scim-okta)，再用[团队 Admin 权限](/cloud/members-and-rbac#team-admin-access)显式批准这个已同步的团队。

## 问题排查

| 现象 | 可能原因 | 解决办法 |
| --- | --- | --- |
| `Provider domain has not been verified` | TXT 记录缺失、被加在域名根节点上，或尚未生效 | 把 token 放在 `_better-auth-token-<provider-id>.<domain>`，等待公网 DNS 生效，然后选择 **Verify domain** |
| `invalid_saml_configuration` | OpenWork 的构建版本没有把生成的 ACS 回调 URL 持久化到 SAML 提供商中 | 升级到包含 SAML 回调配置修复的版本，然后重新编辑并保存该连接 |
| `invalid_audience` | Okta 的 Audience URI 与 OpenWork 配置的 auth origin 不一致 | 使用该部署显示的 OpenWork Web/auth origin，不要替换成另一个 API 主机 |
| `invalid_destination` 或 `invalid_recipient` | Okta 发送到的 URL 与 OpenWork 期望的不同 | 把生成的 OpenWork ACS URL 复制到 Okta，并保留 `Use this for Recipient URL and Destination URL` 处于启用状态 |
| `Invalid SAML response` | 断言未签名、使用了已废弃的算法，或 Okta 当前生效的证书与 OpenWork 中的不一致 | 用 RSA-SHA256 对断言签名，并把 Okta 当前生效的 X.509 证书粘贴到 OpenWork |
| Okta 拒绝访问 | 该用户没有被指派到这个应用 | 在 **Assignments** 下指派测试用户 |
| OpenWork 显示 `Verify the SSO domain before testing this configuration` | DNS TXT 证明还没有通过 | 创建 OpenWork 提示的 TXT 记录，等待 DNS 生效，然后选择 **Verify domain** |
| 测试对话框显示 `The SSO authentication window was closed before the test completed` | 在 OpenWork 收到测试结果之前，弹窗被关闭或被重定向走了 | 重新发起一次测试，并保持认证窗口打开，直到它返回或自行关闭 |
| 修改设置后 OpenWork 不肯启用 SSO | 当前配置还没有成功通过测试 | 再次运行 **SSO Login**，测试成功后再选择 **Enable SSO** |
