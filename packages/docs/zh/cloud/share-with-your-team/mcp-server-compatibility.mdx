这一页面向运行 MCP 服务器、而 OpenWork 成员想要连接它的人：托管远程 MCP 服务器的 SaaS 提供商，或自建服务器的团队。这里逐条列出 OpenWork 在登录过程中发送什么，以及你的授权服务器必须接受什么。

OpenWork 通过 OpenWork Cloud（Den）代表组织连接 MCP 服务器。每位成员通过浏览器用自己的账户登录你的服务器，OpenWork 在服务端保存该成员由此产生的 token，随后 [OpenWork MCP 网关](/cloud/run-in-the-cloud/cloud-mcp)把你的工具暴露给该成员的 AI 应用。因此 OpenWork 是一个 OAuth 客户端、代表众多成员、托管在固定 origin 上。如果你的授权服务器只接受它已知的客户端，OpenWork 必须在其中。

## 检查清单

做到以下几点，OpenWork 侧无需任何手工配置即可连接：

1. **按 MCP 授权规范公布 OAuth。** 对未认证的 MCP 请求返回 `401`，并带上 `WWW-Authenticate: Bearer` 质询，其中的
   `resource_metadata` 指向你的受保护资源元数据（RFC 9728）。
   该文档会列出你的 `authorization_servers`，而每个授权服务器都会发布自身的元数据（RFC 8414）。
2. **支持带 PKCE 的公开客户端。** `code_challenge_methods_supported`
   包含 `S256`，`token_endpoint_auth_methods_supported` 包含 `none`，
   且 `grant_types_supported` 包含 `authorization_code` 和
   `refresh_token`。
3. **以三种方式之一接受 OpenWork 作为客户端**，按 OpenWork 的优先顺序：
   - **Client ID Metadata Document（推荐）。** 公布
     `client_id_metadata_document_supported: true`，并接受
     `https://api.openworklabs.com/oauth/client-metadata.json` 作为
     `client_id`。无需手工加白名单。
   - **动态客户端注册。** 发布一个 `registration_endpoint`，并允许下面的重定向 URL。如果你把注册限制在重定向主机的白名单内，请添加 `api.openworklabs.com`。
   - **预注册客户端。** 给 OpenWork 签发一个 `client_id`（如果你要求密钥，再给一个 secret），绑定到下面的重定向 URL。OpenWork 管理员把它们粘贴进连接。
4. **在所有校验重定向 URL 的地方注册这个精确地址**：

   ```text
   https://api.openworklabs.com/v1/mcp-connections/oauth/callback
   ```

5. **登录后能应答 MCP 会话。** 签发 token 后，OpenWork 会先打开会话（`initialize`）并列出工具（`tools/list`），然后才把连接报告为可用。这些响应必须是 MCP JSON，或带标准 `Content-Type` 的事件流；在这里返回登录页、门户 HTML 或代理错误页都会让连接失败。

<Note>
**自托管的 OpenWork。** 把 `https://api.openworklabs.com` 替换为正在发起连接的实例的
`DEN_API_PUBLIC_URL`。该实例在 `<DEN_API_PUBLIC_URL>/oauth/client-metadata.json`
提供自己的客户端元数据文档，重定向 URL 是 `<DEN_API_PUBLIC_URL>/v1/mcp-connections/oauth/callback`。
各提供商会精确比对重定向 URL，包括协议、主机、端口和路径。
</Note>

## OpenWork 发送什么

OpenWork 的客户端元数据文档，同时也是它动态注册请求的请求体，内容如下：

```json
{
  "client_id": "https://api.openworklabs.com/oauth/client-metadata.json",
  "client_name": "OpenWork",
  "application_type": "web",
  "redirect_uris": ["https://api.openworklabs.com/v1/mcp-connections/oauth/callback"],
  "grant_types": ["authorization_code", "refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "none"
}
```

你可以自行获取在线文档
`https://api.openworklabs.com/oauth/client-metadata.json` 加以确认。

该客户端的其他特征：

- **公开客户端。** OpenWork 只用 PKCE 认证 token 请求；除非你给它签发过带密钥的预注册客户端，那种情况下会使用那个密钥。
- **state。** OpenWork 发送自己签名的 `state` 值，并要求在重定向时原样回传，这是 OAuth 规范要求的。
- **Resource indicator。** 当你的受保护资源元数据声明了
  `resource` 时，OpenWork 会在授权请求和 token 请求中带上它
  （RFC 8707），使签发的 token 专门面向你的 MCP 服务器。
- **Issuer 校验。** 如果你公布
  `authorization_response_iss_parameter_supported: true`，请在重定向时带上 `iss`；OpenWork 会拿它与自己选定的授权服务器比对。
- **作用域。** OpenWork 请求你的 `WWW-Authenticate`
  质询中列出的作用域，回退到受保护资源元数据里的 `scopes_supported`；当你同时支持 refresh token 和该作用域时，会追加 `offline_access`。
- **每个连接只对应一个授权服务器。** 如果你的受保护资源
  元数据列出了多个 `authorization_servers`，OpenWork 管理员必须先选定一个，成员才能连接。

## 登录流程如何走

<Steps>
  <Step title="发现">
    OpenWork 向你的服务器 URL 发送一个未认证的 MCP 请求。从
    `401` 质询中（没有该头部时读取 well-known 路径）它读取你的受保护资源元数据，随后读取每个授权服务器的元数据，并校验 issuer 是否匹配。
  </Step>
  <Step title="客户端注册">
    OpenWork 选择第一个可用的方式：配置过管理员提供的预注册客户端就用它；否则在你公布了相应支持时使用 Client ID Metadata Document；再否则在你发布 `registration_endpoint` 时使用动态注册。都不满足时，连接会等待管理员添加预注册客户端。
  </Step>
  <Step title="授权">
    成员的浏览器被送往你的 `authorization_endpoint`，携带 PKCE
    （`S256`）、OpenWork 的 `state`、上面的重定向 URL、前文描述的作用域，以及适用时的 resource indicator。你展示同意页，然后带 code 重定向回来。
  </Step>
  <Step title="换取 token 并校验">
    OpenWork 在你的 `token_endpoint` 上用 code 换取 token，为该成员保存 token，然后带着新的访问令牌对你的 MCP 服务器执行 `initialize` 和 `tools/list`。只有工具列表成功返回，成员才会被标记为已连接。
  </Step>
  <Step title="刷新">
    访问令牌过期时，OpenWork 用 refresh token 续期并重跑同一套校验。轮换出的新 refresh token 按签发时的值保存。
  </Step>
</Steps>

## 注册方式详解

### Client ID Metadata Document

这是当前 MCP 授权规范推荐的注册机制，也是 OpenWork 首选的方式。你的授权服务器按 URL 抓取 OpenWork 的元数据文档，因此没有逐部署审批，也不需要保存注册记录。如果你已经支持它，OpenWork 无需你做任何操作即可连接；如果你维护已批准客户端元数据 URL 的白名单，请加入
`https://api.openworklabs.com/oauth/client-metadata.json`。

### 动态客户端注册

OpenWork 每个连接向你的 `registration_endpoint` 提交一次上面的元数据来注册自己。许多服务器在这里接受任意 `redirect_uris`；有些只接受回环地址或主机白名单。后一种情况下，请放行主机 `api.openworklabs.com`（或精确的重定向 URL）。注册被以 `invalid_redirect_uri` 拒绝，或以 `invalid_request` 拒绝且描述里点名了重定向 URI 时，成员看到的就是下文的
`MCP_OAUTH_REDIRECT_URI_NOT_ALLOWED`。

### 预注册客户端

如果你的授权服务器既不公布客户端元数据文档，也不发布 `registration_endpoint`，OpenWork 就无法自行注册。请像为你手工批准的其他 AI 客户端一样，给 OpenWork 签发一个客户端，并绑定上面的重定向 URL：

- 公开客户端（`token_endpoint_auth_method: none`）就够了。如果你的服务器要求密钥，就签发一个，OpenWork 会把它保存在服务端。
- 授予 `authorization_code` 和 `refresh_token`。
- 把 `client_id`（以及密钥）交给 OpenWork 组织管理员。他们在 OpenWork Cloud 中打开 **Manage › Connectors › Add connector**，粘贴你的 MCP 服务器 URL，在 **Client ID** 和 **Client secret** 下填入这些值，然后点击 **Save app**。对于已存在的连接器，他们打开其 **Settings**，点击 **Add OAuth app**，再点击 **Save changes**。需要注册的 URL 见[与团队共享 MCP 连接](/zh/cloud/share-with-your-team/shared-mcp-connections)。

<Warning>
一个「用你的产品登录」的 OAuth 应用，如果它的 token 只对你的 REST API 有效，那它帮不上忙——只要你的 MCP 服务器拒绝这些 token。你签发的客户端必须能产出你的 MCP 资源接受的 token。
</Warning>

## 缺步骤时成员会看到什么

OpenWork 里每一次失败的连接尝试都带一条诊断信息，包含阶段、错误码、谁能修复，以及一个参考 ID。成员看到的是通俗说明，管理员可以展开技术细节。最常见的提供商侧原因：

| 你的服务器的表现 | 成员看到的诊断 | 需要改什么 |
| --- | --- | --- |
| 动态注册返回 `400 invalid_redirect_uri`，或返回 `invalid_request` 且点名重定向 URI | `MCP_OAUTH_REDIRECT_URI_NOT_ALLOWED`：提示「*Provider* hasn't approved OpenWork yet」，并给出要加白的重定向 URL 和参考 ID。成员会被告知重试没有用。 | 为注册放行 `api.openworklabs.com`，接受 OpenWork 的客户端元数据 URL，或签发一个预注册客户端。 |
| 授权服务器元数据既没有 `registration_endpoint`，也没有 `client_id_metadata_document_supported` | **Knows how you sign in** 检查项显示「*Provider* needs your OAuth app.」。在有管理员填入 **Client ID** 之前，连接器无法连接。 | 给 OpenWork 签发客户端，或者支持客户端元数据文档或动态注册。 |
| 返回 `401` 但 `WWW-Authenticate` 没有 resource 元数据，也找不到可发现的受保护资源文档 | OpenWork 把该服务器视为 API 密钥或 bearer token 认证，并向管理员索要密钥。 | 发布 RFC 9728 元数据，并在质询中带上 `resource_metadata` 参数。 |
| 因其他原因被拒（`invalid_client_metadata`、不支持的 grant 或认证方式） | `MCP_OAUTH_CLIENT_REJECTED`，详情里带上提供商返回的错误码。 | 接受上文展示的元数据：公开客户端、`authorization_code` + `refresh_token`、`response_types: ["code"]`。 |
| 受保护资源元数据列出多个 `authorization_servers` | 管理员必须先选定一个登录服务器（连接 **Settings** 中的 **Review sign-in server**），成员才能连接。 | 无强制要求；issuer 越少，就越接近一键配置。 |
| 授权服务器元数据里的 issuer 与公布的 issuer 不一致 | `MCP_OAUTH_ISSUER_MISMATCH` | 让元数据文档中的 `issuer` 与 `authorization_servers` 里列出的 URL 一致。 |
| `tools/list` 或 `initialize` 返回 HTML，或返回非 MCP 的 `Content-Type` | `MCP_HTTP_HTML_RESPONSE` 或 `MCP_HTTP_CONTENT_TYPE` | 提供 MCP JSON 或 `text/event-stream`；把登录页和代理错误页移出 MCP 路径。 |
| 任意步骤返回 `429` | `MCP_HTTP_429`，会以有限退避重试 | 标准的限流响应头有帮助；没有其他要求。 |

成员可以复制的参考 ID（`req_…`）用于在 OpenWork 的日志中定位这次尝试。如果成员把它分享给你，其中就编码了尝试的确切时间，OpenWork 支持可以据此匹配你的服务器实际收到的请求。

## 申请模板

需要请提供商批准 OpenWork 的成员和管理员，可以把这段发出去：

> 我们使用 OpenWork（openworklabs.com）把团队连接到你们托管在
> `<your MCP server URL>` 的 MCP 服务器。目前登录在客户端注册这一步失败，因为 OpenWork 的重定向 URL 未被批准。请任选一种：(a) 接受我们的 Client ID Metadata Document `https://api.openworklabs.com/oauth/client-metadata.json` 作为 client_id；(b) 为动态客户端注册放行重定向 URL
> `https://api.openworklabs.com/v1/mcp-connections/oauth/callback`（主机
> `api.openworklabs.com`）；(c) 给 OpenWork 签发一个绑定该重定向 URL 的预注册 OAuth 客户端：使用 PKCE S256 的公开客户端，授予 `authorization_code` 与 `refresh_token`。客户端名称为 OpenWork。失败尝试的参考 ID：`<req_… from the connection error>`。
