按成员绑定的凭证，让组织可以把一个托管 LLM 提供商授予许多人，而不共享同一个上游密钥。当外部网关（例如 LiteLLM）为每个成员签发独立的虚拟密钥时，就用这种模式。

这一页讲的是一种 API 集成方式。Den 并不内置 LiteLLM 的密钥签发和元数据发现：你要针对 Den 通用的提供商与凭证绑定路由，加上 LiteLLM API，自行运行一个 provisioner（供给器）。

## 适用位置

- 按成员凭证适用于[旧式提供商](/zh/cloud/share-with-your-team/managed-llm-provider)，即 `/v1/llm-providers` API。Cloud 控制台没有对应的设置项：请通过 API 设置 `credentialMode`。创建完成后，该提供商会和其他提供商一起出现在 **AI Gateway › AI Providers › Legacy Providers** 下。
- 成员无法在桌面应用里输入自己的密钥。他们的密钥来自你的 provisioner，或来自下文的成员路由。在成员拥有生效的绑定之前，桌面应用会把该提供商列为 **Needs organization credential**，其模型也不可用。
- 如果你需要的是按成员各自登录，而不是按成员各自的密钥，AI 网关提供商对 [Google Vertex AI](/ai-gateway/google-agent-platform)、[Amazon Bedrock](/ai-gateway/amazon-bedrock) 和 [Microsoft Foundry](/ai-gateway/microsoft-foundry) 支持 **Each member signs in**。密钥留在服务端，用量按人统计。

## 选择凭证模式

在创建或更新组织 LLM 提供商时设置 `credentialMode`：

- `shared` 只存储一份提供商凭证。每个被授予的成员通过 connect 路由拿到的都是这一份。
- `per_member` 为发起调用的组织成员解析各自绑定的凭证。提供商可以在绑定存在之前就先授予。

用 `POST /v1/llm-providers` 创建一个按成员的自定义提供商：

```json
{
  "name": "Per-member gateway",
  "source": "custom",
  "customConfig": {
    "id": "per-member-gateway",
    "name": "Per-member gateway",
    "npm": "@ai-sdk/openai-compatible",
    "env": ["GATEWAY_API_KEY"],
    "api": "https://gateway.example.com/v1",
    "models": [{ "id": "team-model", "name": "Team model" }]
  },
  "credentialMode": "per_member",
  "allMembers": true
}
```

这些请求要带上组织的 bearer token 以及 `x-openwork-org-id` 请求头。

## 成员侧流程

被授予的成员只能操作属于自己的、只写的凭据材料：

- `PUT /v1/llm-providers/:id/my-credential`，请求体只能是 `{ "apiKey": "..." }` 或 `{ "apiKeys": { "ENV_NAME": "..." } }` 中的一个
- `DELETE /v1/llm-providers/:id/my-credential`
- `GET /v1/llm-providers/:id/connect`，用于获取提供商配置以及解析后的本人凭证

对被授予的成员，connect 路由始终返回 HTTP `200`。当成员没有生效的绑定时，它保持标准的提供商响应结构，把两个凭证字段都留空，并报告该成员的状态：

```json
{
  "llmProvider": {
    "apiKey": null,
    "apiKeys": null,
    "memberCredential": { "state": "missing" }
  }
}
```

`memberCredential.state` 取 `missing`、`active`、`blocked`、`stale` 或 `error` 之一。生效(active)的响应会带上该成员解析出的 `apiKey` 或 `apiKeys`；其他所有状态都返回空凭证。missing 或 blocked 之所以是响应数据而不是错误状态码，是因为已发布的桌面客户端在 connect 响应非 OK 时会让整个提供商同步失败。较旧的客户端本就能安全降级：connect 载荷里没有可用凭证时，它们会跳过该提供商。

成员的 OpenWork Web 实例得到的是同一套解析结果：Den 只把该成员自己生效的绑定写入实例，绝不会写入队友的；当成员没有生效绑定或未被授予该提供商时，就不把该提供商写入。轮换后的绑定会在实例下次被使用时写入。

Cloud Automations 运行在其所有者的 OpenWork Web 实例上，因此同样使用该实例所有者的绑定。当某个 Automation 的模型属于按成员提供商，而实例所有者没有生效绑定时，这次运行会在调用模型之前就停止，并且该 Automation 会被标记为需要处理，原因里会点名该提供商。请先为这位所有者签发凭证绑定，再恢复该 Automation。

## 管理员与 provisioner 侧流程

组织所有者和管理员可以用以下路由运行一个集中式 provisioner：

- `GET /v1/llm-providers/:id/member-credentials` 列出每个被授予成员的状态、版本和外部标识符，绝不返回任何凭据材料。
- `PUT /v1/llm-providers/:id/member-credentials/:orgMembershipId` 存储单个成员的凭证。请求体接受 `apiKey` 或 `apiKeys`，以及可选的 `externalPrincipalId`、`externalCredentialId` 和 `expectedVersion`。
- `POST /v1/llm-providers/:id/member-credentials/:orgMembershipId/block` 把已有绑定标记为 blocked。

当多个 provisioner 工作进程可能更新同一个绑定时，请使用 `expectedVersion`。版本不匹配会返回 HTTP `409`，响应体为 `{ "error": "version_conflict" }`。

blocked 状态的绑定归管理员所有，成员无法覆盖或删除它：成员的写入和删除都会返回 HTTP `409`，响应体为 `{ "error": "credential_blocked" }`。管理员发起的 `PUT` 就是显式的解封并替换路径。

## LiteLLM 示例

可运行的示例位于 [`examples/litellm-per-member-keys`](https://github.com/different-ai/openwork/tree/dev/examples/litellm-per-member-keys)，使用 LiteLLM 虚拟密钥。按该示例 README 中列出的项配置 Den 与 LiteLLM 的 URL、管理员 token、提供商 ID 和模型 ID，然后运行：

```bash
node provision.mjs reconcile
```

示例首先通过 `GET /v1/llm-providers?scope=manageable` 读取那个精确的提供商，确认它是一个自定义的 `per_member` 提供商，然后用主密钥查询 LiteLLM 的 `GET /model_group/info`。每个已配置的模型都必须有精确匹配的 `model_group`，以及有限的正数 `max_input_tokens` 和 `max_output_tokens`。provisioner 用这些信息更新每个 Den 模型的上下文、输入和输出上限。若 LiteLLM 返回了函数调用、推理、视觉、响应结构和温度这些事实，示例会把它们映射为 `tool_call`、`reasoning`、`attachment`、`structured_output` 和 `temperature`。整份替换会保留完整的提供商配置、已有的模型字段、凭证模式，以及全部成员/团队访问规则。

如果元数据或上限缺失，这一步会在签发密钥之前失败(fail closed)。它绝不猜测 token 上限，也不回退到某个通用值。Den 的整份替换 PATCH 不发送 `apiKey` 和 `apiKeys`，因此 Den 会保留那份只写的已存凭证；当提供商已经同步一致时，示例会完全跳过这次 PATCH。

随后它补齐缺失的成员凭证：

```js
const { memberCredentials } = await den.get(
  `/v1/llm-providers/${providerId}/member-credentials`,
)

for (const binding of memberCredentials) {
  if (binding.state !== "missing") continue

  const keyAlias = `openwork-${binding.orgMembershipId}`
  const minted = await liteLlm.post("/key/generate", {
    models,
    key_alias: keyAlias,
    metadata: {
      openwork_org_membership_id: binding.orgMembershipId,
    },
  })

  await den.put(
    `/v1/llm-providers/${providerId}/member-credentials/${binding.orgMembershipId}`,
    {
      apiKey: minted.key,
      externalCredentialId: minted.token_id,
    },
  )
}
```

LiteLLM v1.97 会返回一个 `token_id`，凭它就能定位这张虚拟密钥，而不必保留明文密钥值。示例把该标识符存入 `externalCredentialId`；之后 Den 的管理端列表可以安全地把它返回给 provisioner。

`/model_group/info` 调用与字段映射是刻意放在这个 LiteLLM 专用示例里的。Den 内核保持厂商中立：它的提供商 PATCH 和按成员凭证 API 只接受解析后的通用模型配置，不硬编码 LiteLLM 的行为。

### 按安全顺序做离职处理

一定要**先**吊销或封禁上游凭证，**再**移除它在本地的落地副本。如果上游调用失败，就让 Den 的绑定保持 active，这样失败会一直可见、可重试，而不是报告一个并不存在的本地封禁。

以该示例为例：

1. 从 `GET /v1/llm-providers/:id/member-credentials` 读取该成员的 `externalCredentialId`。
2. 调用 LiteLLM 的 `POST /key/block`，请求体为 `{ "key": "<token_id>" }`，并确认成功。
3. 调用 Den 的 `POST /v1/llm-providers/:id/member-credentials/:orgMembershipId/block`。
4. 确认该成员的 connect 请求返回 HTTP `200`、凭证为空，且 `memberCredential.state: "blocked"`。

运行 `node provision.mjs offboard <orgMembershipId>` 即可执行这一串操作。这套集成已针对真实的 LiteLLM 数据库和一个冷启动的 Den 验证过，见 `evals/specs/litellm-per-member-credentials.e2e.test.ts`。
