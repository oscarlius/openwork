本页汇总一个团队运行 OpenWork Cloud 或私有 OpenWork 部署时真正重要的安全与运维控制项。

OpenWork 是本地优先的，但 Cloud 加上了共享身份、成员、RBAC、托管工作进程、共享提供商和组织策略。请把 Cloud 当作团队访问与共享运行时状态的控制面。

## 加密与传输

生产部署应当强制加密传输和加密存储：

- Cloud 应用、Den API、OAuth 回调、webhook 入口和工作进程控制流量都走 HTTPS。
- 在边缘或负载均衡器终止 TLS，并且只通过受信任的私有网络转发。
- 为生产数据库、对象存储、备份，以及可能包含运维元数据的日志启用静态加密。
- 本地开发的默认值就留在本地。仓库脚本里的示例开发数据库 URL 和本地密钥不是生产设置。

OpenWork Cloud 的托管 Den 数据库跑在 PlanetScale 上。PlanetScale 会对数据库存储和备份做静态加密，并且 PlanetScale 的数据库连接串要求先建立 TLS 才能发出 SQL 命令。OpenWork 的生产迁移流程还会为 PlanetScale 的 MySQL 协议连接配置严格的 TLS 校验。

OpenWork 还会用应用层的 AES-256-GCM 加密（密钥是 `DEN_DB_ENCRYPTION_KEY`）加密选定的敏感数据库列，例如提供商密钥和 SSO 配置。这是一项附加控制，不替代提供商管理的静态存储加密。

对于私有或自托管部署，运维方负责在目标环境里启用 TLS 证书、数据库存储加密、备份加密和私有网络策略。

## 密钥与凭据

生产密钥应当存放在托管的密钥系统或 KMS 支撑的环境里，而不是提交进文件或共享的 shell 历史里。

按环境分别使用不同的密钥，覆盖：

- Better Auth 的签名与会话密钥
- 数据库加密材料
- OAuth、SSO、SCIM 和 webhook 密钥
- 提供商 API 密钥与工作进程开通令牌

OpenWork 以哈希形式保存组织 API 密钥和 SCIM bearer token。SSO 提供商配置以加密形式存储。生产密钥要按既定周期轮换，并在怀疑暴露或使用过紧急访问之后立即轮换。轮换 SCIM token 会让前一个 bearer token 失效；轮换后请立即更新身份提供商。

## 身份与访问治理

请把 Cloud 的成员模型当作组织访问的唯一事实来源：

- 保护好 `Owner` 账户，并维护一条经过验证的恢复路径。
- 日常运维人员用 `Admin`。设置与访问管理（组织设置、SSO、SCIM、API 密钥、成员角色、Admin 团队）默认留在所有者手里，除非企业版组织通过 Permissions 授予出去。
- 大多数人保持 `Member`。
- 用团队来控制对 Collection 和提供商的资源访问。

SSO 即时开通对首次登录用户在 SAML 认证成功后使用 `Member` 作为安全默认值。标准登录流程会把已验证、已启用的 SSO 域名下的邮箱地址路由到 SSO。用同一域名做独立的邮箱/密码注册本身不会给予组织成员身份。在 SSO 登录过程中，OpenWork 不会把 IdP 的属性（例如 `role`、`groups` 或 `admin`）转换成组织角色。更高的权限需要明确的 OpenWork 角色指派、所有权转移，或一个已批准的 Admin 团队。

所有者可以批准一个手动维护或 SCIM 管理的团队来授予组织 `Admin`。复核时既要看直接角色，也要看 **Admin via** 的来源：移除一个授权不会移除其他授权。对于 SCIM Admin 团队，访问复核要把 IdP 的群组管理权限和开通延迟一并纳入。审批、撤销与映射重置的保护措施见[团队 Admin 权限](/zh/cloud/members-and-rbac)。

做访问复核时，请按固定周期导出当前的成员清单、角色、团队、待处理邀请、API 密钥、SSO 配置和 SCIM 配置。请重新确认每位成员是否仍需要当前的角色和团队访问。

## MFA 与 step-up 控制

对生产组织，请把带身份提供商 MFA 的 SSO 作为主要的 step-up 控制：

- 对已经拥有所有者、管理员、SCIM、SSO、API 密钥或共享生产提供商的组织，启用强制 SSO。
- 在用户抵达 OpenWork Cloud 之前，先在身份提供商里要求 MFA、可用的抗钓鱼认证因子和条件访问策略。
- SSO、SCIM、API 密钥管理和 Admin 团队指定默认都是所有者专属。直接或继承的 `Admin` 不包含它们；企业版组织可以有意识地通过 Permissions 授予。
- 管理员只能邀请 `Member` 用户。所有者可以邀请管理员，但不能邀请另一个 `Owner`；所有权只能通过转移产生。
- 在通过特权路由修改 SSO、SCIM、API 密钥、组织设置、成员角色、结算或推理设置之前，服务器要求会话是最近 15 分钟内创建的。
- 除非该部署在 OpenWork 之外有等价的 MFA 与恢复控制，否则不要把独立的邮箱/密码账户当作生产的所有者访问方式。

原生认证因子注册和产品内重新认证，应当被视为在替代 SSO 强制 MFA 这项生产控制之前需要完成的产品工作。

## 标准邮箱/密码的保护

OpenWork Cloud 的标准邮箱/密码路径在服务端受到保护，可抵御大流量猜测和已泄露的已知密码：

- 邮箱/密码登录有速率限制。默认登录规则在 5 分钟窗口内允许 5 次尝试，在此之外还有 Better Auth 的全局限流。
- 失败的邮箱/密码登录按账户标识的哈希来追踪。最近失败达到 5 次后，账户进入渐进锁定：先是 5 分钟，持续失败则锁定更久，上限 1 小时。登录成功会清除失败计数。
- 创建密码和重置密码时，会用 `Have I Been Pwned` 的 Pwned Passwords range API 检查待设密码。OpenWork 只发送该密码 SHA-1 哈希的前 5 个字符，用 k-匿名响应在本地比对后缀，并拒绝已知的被泄露密码。
- 如果密码检查暂时不可用，创建密码或重置会失败关闭，并请用户稍后再试。

OpenWork 在正常登录过程中不会调用被泄露密码服务。已有密码的登录应依靠速率限制、锁定、身份提供商控制、监控，以及凭据后续被怀疑泄露时的强制重置流程来保护。

没有对外网络出口的私有部署可以用 `DEN_PASSWORD_BREACH_SCREENING_ENABLED=false` 关闭被泄露密码检查。Helm chart 对隔离的自托管安装默认设置 `config.auth.passwordBreachScreeningEnabled: "false"`。这会去掉对外部 range API 的依赖，也去掉已知被泄露密码的拒绝。

关于人员调入调出的处理：

- 职责变化时同步改变角色。
- 不再需要访问时移除成员。
- 取消过期邀请。
- 轮换或吊销为该成员签发过的组织 API 密钥。
- 在身份提供商是记录系统的地方，优先使用 SCIM 撤销开通。

SCIM 生命周期失败不能被当作成功的离职处理。OpenWork 会记录失败的 SCIM 开通与撤销工作以便重试，运行周期的本地 SCIM 漂移对账，并在组织的 SCIM 界面暴露尚未解决的 SCIM 健康问题。运维方应当监控这些健康指标，并把包含 `[scim][sync_failure_recorded]` 或 `[scim][maintenance_failed]` 的 Den API 日志接入自己的告警系统。

## 紧急访问

请在需要之前就规划好紧急访问。

推荐模式：

- 保留一个 break-glass 的 `Owner` 账户或等价的恢复路径。
- 用该部署中可用的最强认证方式保护它。
- 把凭据存放在受控的紧急保险库里。
- 对任何一次使用都发出告警。
- 使用后审阅审计轨迹。
- 如果紧急访问可能暴露了凭据或签名材料，就轮换它们。

不要把 break-glass 账户用于日常管理等常规操作。

## 审计事件

OpenWork 会为特权的 Cloud 操作记录结构化的组织审计事件，包括：

- API 密钥的创建与删除
- 成员角色变更与成员移除
- 邀请的创建、刷新与取消
- 自定义角色的创建、更新与删除
- SCIM token 轮换与连接删除
- SSO 的注册与删除

审计载荷不会带上 bearer token、API 密钥机密、SCIM token、SAML 证书和 OIDC 客户端密钥。敏感的访问变更还会输出结构化的 `[audit-alert]` 日志行，方便运维方把 SSO、SCIM、API 密钥、角色、邀请和成员变更事件接入告警。对于私有部署，请通过部署的数据库或日志管线把审计数据和 audit-alert 日志导出，进入组织的留存与 SIEM 流程。

## 可用性与故障转移

OpenWork Cloud 把 Den API 视为身份、RBAC、托管工作进程、共享提供商和组织策略的逻辑控制面。托管部署会避免让这个逻辑控制面成为单一物理瓶颈：

- Render 把 Cloud 应用和 Den API 作为可伸缩服务运行，生产流量至少两个实例。
- Render 在健康实例之间负载均衡，停止把请求路由到健康检查失败的实例，并重启失败的实例。
- Den API 实例是无状态的应用副本；共享状态存放在 PlanetScale 和外部托管服务里。
- PlanetScale 生产集群提供一个主库和至少两个副本，分布在三个可用区，故障转移由 PlanetScale 自动管理。
- PlanetScale 的自动备份在 Base 套餐上至少每 12 小时运行一次；运维方还应根据自己的套餐定义留存策略、恢复演练和 point-in-time recovery 的预期。

生产与私有部署都应避免单节点控制面：

- 把 Cloud 应用和 Den API 跑在健康检查之后。
- 在平台支持的情况下运行多个 API 实例。
- 使用带自动备份与故障转移的托管数据库，例如 PlanetScale 生产分支或等价的 MySQL 兼容高可用服务。
- 监控 API 健康、工作进程开通、队列深度、webhook 失败、登录失败和数据库连通性。
- 为数据库、对象存储和工作进程状态定义恢复目标。
- 在事故之前演练恢复与故障转移流程。

对于自托管部署，请记录确切拓扑：入口、应用、API、工作进程开通、数据库、备份、故障转移负责人、恢复负责人，以及每个部分的责任人或团队。
